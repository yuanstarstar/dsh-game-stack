# dsh-cv-recall · 感知编译器

把「看一眼画面」编译成「每帧跑几十毫秒的本地代码」，让 DSH 打游戏时不必每次都截图问模型。

一个问题、一个答案：

> 模型识图 1.5~3k token、1~10 秒；而游戏界面里的血条、小地图、技能图标，**位置固定、外观固定**，
> 真正在变的只有数字和内容 —— 那就别反复问模型，让它看一次、把「认什么、在哪」编译成资产，
> 之后每帧用纯 numpy 认。

| | 现在 | 编译后 |
|---|---|---|
| 每次看盘面 | 1.5~3k token / 1~10s | **0 token** / 50~80ms（11 个实体，1280x720，纯 numpy） |
| 输出 | 一段自由文本（要解析） | 结构化 JSON（`scene` / `entities` / `changed` / `stale`） |
| 画面变了 | 看不出来 | 自己报 `stale: true` |

## 三个工具

### `cv_learn` —— 编译（一次性）

| action | 干什么 |
|---|---|
| `scan` | 截一帧，本地提议器**免费**给出候选框（颜色连通域 + 边缘连通域 + NMS），`attach:true` 才把框画在图上 |
| `build` | 用候选编号或坐标编译实体；`packId` 固定，多个场景 `append:true` 并进一个包 |
| `add_scene` | 再加一个场景：用这一帧顺手校准「谁在谁不在」的阈值，**不用重新标框** |
| `list` / `get` / `delete` | 管理资产 |
| `windows` | 列出可见窗口（拿 `hwnd` / 标题） |

关键设计：**模型只给坐标和名字**。颜色直方图、梯度方向、结构哈希、分块相关，全部由本地代码
从框内像素自己算 —— 模型描述外观既费 token 又不准，而本地算一遍只要几百微秒。

```
cv_learn{action:"scan"}
→ #1  424x100  暗色  边缘0.12  33%,2%   color
  #2  192x192  暗色  边缘0.31  84%,72%  edge
  ...                                   ← 挑你要的编号

cv_learn{action:"build", packId:"wow", game:"某个游戏", scene:"battle",
         picks:[{n:1, id:"portrait", label:"头像"}, {n:4, id:"hp_frame", label:"血条"}]}

cv_learn{action:"add_scene", packId:"wow", scene:"dialog",
         present:["portrait","hp_frame"], absent:["skill1","skill2"]}   ← 不用再标

cv_learn{action:"build", packId:"isaac", scene:"start_room",
         picks:[{id:"one_heart", label:"血条"},
                {id:"coin", label:"金币", digits:{box:[196,290,112,72], value:"00"}},
                {id:"enemy_hp", label:"敌人血量", digits:{box:[700,120,120,40], value:"40"}}],
         derived:[{id:"hp", label:"血量", from:["heart_1","heart_2","heart_3"], agg:"count"}]}
         ↑ digits: 这一格是数字 + 这一帧上是几 → 顺手学字形，之后每帧本地读
         ↑ derived: 画面上没有、靠在场实体算出来的数（血量 = 在场红心数）
```

### `cv_recall` —— 读盘（每帧）

```
cv_recall{}
→ 场景 battle（conf 96%，距离 0.083）· 变化 12 格 · 72ms
  ✓ portrait 93% [40,18,96,96]
  ✓ hp_frame 88% [120,22,320,18]
  · 不在：choice_cursor
```

参数：`packId`（省略用唯一的包）、`only:["hp_frame"]`（省 token）、`boxes:true`（要坐标）、
`hwnd` / `title` / `path`（默认当前前台窗口）、`text:[[x,y,w,h]]`（顺手读几块文字）、
`novel:true`（找出画面上没编过的新东西）。

**数值与描述**（`values` / `labels`，默认都开）：

```
cv_recall{values:true}
→ 场景 start_room（conf 96%，距离 0.022）· 变化 首帧 · 211ms
  ✓ 红心1 94% [370,146,68,62]
  ✓ 红心2 94% [442,146,68,62]
  ✓ 红心3 94% [514,146,68,62]
  ✓ 金币 = 0 94% [150,300,40,54]
  ✓ 炸弹 = 1 94% [146,368,44,56]
  ✓ 钥匙 = 0 94% [143,432,44,60]
  · 数值：血量 3
```

描述来自编译时的 `label`，数值来自两条路：

- **读数字**：`picks` 里给 `digits:{box:[x,y,w,h], value:"00"}` —— `value` 是这一帧上的真实数字，
  工具顺手把字形学进**包级字形图集**，之后每帧只跑像素比对（`pcv/digits.py`，零模型调用）。
- **派生数值**：`derived:[{id:"hp", label:"血量", from:["heart_1","heart_2","heart_3"], agg:"count"}]`
  —— 「血量」= 在场红心数，所以**三颗心是三个独立实体**，各自报在不在、各自有框；
  缺一颗就是 2。这一点比"整条血条"更准也更像人看盘面的方式。

**这个窗口还没编过包呢？** 不会一句 `Error: 需要 packId` 把你挡住，而是给一帧「空画面」：
场景报 `unlabeled`、实体表是空的，但**帧号有、顺手读到的文字块也有**。

```
cv_recall{text:"bottom"}
→ 场景 unlabeled · 变化 首帧 · 41ms · 帧 f7
  （这个窗口还没有感知包：认不出实体，但帧号和下面的文字块可以拿来点）
  · 先 cv_learn{action:"scan"} 再 build 一个包；现在只能用坐标 click:{x,y}，或文字块（t1/t2…）指路。
  · 文字（bottom）：
    「今日的书籍」 button [742,330,96,26]
```

理由：没包不等于什么都做不了 —— 帧号能拿去点坐标，读到的文字块能按文字点。把这两条路一起
堵掉，才是真的不能用。

### `cv_act` —— 动手（点、打字、按键）

看清之后总要动一下。`cv_act` 不让模型算屏幕坐标：**用 id 指路，坐标由它现算**。

```
cv_recall{text:"bottom"}
→ 场景 battle（conf 96%）· 变化 12 格 · 72ms · 帧 f17
  ✓ 红心1 94% [370,146,68,62]
  · 文字（bottom）：
    「你的回合」 text [96,430,1100,60]
    「继续」 button [104,600,200,60]          ← 文字块自动编号 t1/t2…

cv_act{frame:"f17", click:"继续"}
→ ✓ 点 (…)「继续」· 变化 18 格 · 场景 battle · 96ms
  · 帧 f18（下一步直接用它，别再 recall）
```

一次看、一次动，**0 张截图**。回执里已经给了新帧号，下一次动作接着用 —— 不需要为了点一下重新读盘。

**指路方式**（`click` / `from` / `to` 都吃这几种）：

| 写法 | 含义 |
|---|---|
| `click:"t2"` | 这一帧的第 2 个文字块 |
| `click:"heart_2"` | 感知包里的实体 id |
| `click:"继续"` | 按文字找（精确优先，其次包含，取最短那块） |
| `click:"血量"` | 按编译时写的中文 `label` 找 |
| `click:{x,y}` | 客户区像素坐标（自己算好了才用，属于兜底） |
| `click:"200,126"` / `"(200, 126)"` / `'{"x":200,"y":126}'` | 同上，但坐标是**作为字符串**传进来的 —— 也认 |

最后一行不是凑数：模型有时会把 `{x,y}` 序列化成字符串塞进 `click`，早期版本会拿它去实体表里查，
于是报「帧里没有 `{"x": 509, "y": 187}`」这种看不懂的错。坐标就是坐标，多一层引号也该认。

**它替模型扛掉的四件事**：

1. **坐标属于帧，不属于屏幕**：`from_frame:"f17"` 记的是那一帧的客户区坐标，真按下前才
   `ClientToScreen` 换成屏幕坐标 —— 窗口中途被拖走也不会点偏。
2. **遮挡守卫**：目标位置被别的窗口盖着 → 直接 `TARGET_OCCLUDED`，不发这一下
   （盲点下去等于点到别人身上）。`recover:true` 会试着切一次前台再查；`allow_windows:[hwnd]`
   可以把"弹出的对话框"放进白名单。
3. **键白名单**：`space / esc / enter / 方向 / 字母数字 / F1-F12` 与 `ctrl+shift+t` 这类组合键，
   不是"想按什么就按什么"。
4. **动作后自动回执**：`changed` 是 8×5 网格比上一帧变了多少格（0 = 大概没点到），
   `verify:"scene"` 还会顺手跑一遍感知包，把新场景/新框带上。

**失败也是结构化的一句话**，不是异常栈：

| code | 什么时候 | 该怎么办 |
|---|---|---|
| `NOT_FOUND` | id/文字在这一帧里没有 | 回执里列出了这一帧有什么，重挑 |
| `STALE_REF` | 帧超过 2.5s | 重新 `cv_recall` 拿新帧 |
| `OUT_OF_BOUNDS` | 点落在客户区外 | 坐标算错了 |
| `TARGET_OCCLUDED` | 被别的窗口挡住 | 先切前台，或 `recover:true` |
| `NOT_FOREGROUND` | 键盘动作要求目标在前台 | 同上 |
| `WINDOW_GONE` | 窗口没了 | 换窗口 |
| `INPUT_DISABLED` | sidecar 是带 `--no-input` 起的（插件配置 `input:false`） | 想要动手就去掉这个配置 |
| `UIPI` / `REFUSED` | 目标是提权窗口，SendInput 被拦 | 没办法，只能人工点 |
| `DEADLINE` / `STOPPED` | 批处理超时 / 被 `stop` 打断 | 少走几步，或分两批 |

**批处理**：`action:"batch", steps:[{click:"开始"},{key:"space",repeat:3}]` —— 任一步失败立刻停，
回执里带"走到第几步、为什么停"。`action:"stop"` 只中止进行中的那一批并放开按住的键，
**不是永久开关**（之后照样能继续动；真要彻底停用，用 `--no-input` 启动）。

**为什么没有 `wait`**：等待的本质是"等到画面变成某个样子"，而这件事 `changed` 和下一次
`cv_recall` 已经回答了 —— 模型自己决定看几次，比工具里塞一个猜不准的定时器强。
多一个 `wait` 只会让工具表更长、失败模式更多。

**安全默认**：`inputEnabled` 默认开（装好就能用）。每一次动作都往
`~/.dsh/cv-recall/input-log.jsonl` 追加一行审计（时间、帧号、点了什么、成没成、走了几步），
事后能查"它当时手里是哪一帧、点的哪个 id"。

## 被挡住一半，还认得出来吗？—— 认得出，而且会告诉你"它被挡住了"



整块模板匹配有个软肋：一块东西盖掉半边，归一化互相关是被"平均"掉的（实测角色被盖住左半，
整块 NCC 从 0.94 掉到 0.65，再盖多一点就掉到 0.35 以下）。但**没被盖住的那些格子里，像素还是
严丝合缝的**。所以遮挡这条路走的是"数还剩几块对得上"，而不是"整体像不像"：

- `tile_stats()` 给两个数：`score`（最好的 1/3 块的均值）与 **`cover`（还有多少比例的格子对得上）**。
  `cover` 的分母固定是 3×3=9，"盖住就算数"，所以它不会被"盖住七成但剩下三块都满分"骗过去。
- 编译时每个实体都会记一个**自己的覆盖率基线 `cov0`**（校准帧上的 `cover`）。遮挡判定跟它比，
  不跟 1.0 比 —— 天生带大片纯色的模板（小地图的黑底）永远到不了 1.0。
- 真到"整块 NCC 连位置都定不准"的时候，会走一次兜底：`cover_search()` 把搜索图和模板一起缩小
  4 倍、逐块算 NCC 累加成覆盖热力图，先找到大概位置，再在那个落点上读一次分块读数。
  这条路要 9 次小 FFT（30~80ms），所以**只在必要时做**：场景已确认、某个已知控件却"不见了"，
  才会为它付这笔钱。

输出里因此多了三个字段：`cover`（还看得见多少）、`occluded`（1 = 认出来了，但明显缺了一块）、
`via`（`"-"` 常规 / `"cover"` 靠覆盖率认定 / `"occl"` 靠兜底搜索找回）。

实测（《以撒》真实截图，9 实体，遮挡物用**确定性噪声纹理**而不是纯色块 —— 纯白块去盖亮图标时，
色块自己就跟图标长得像，测出来的"误报"其实是测试数据的问题）：

| 实体（模板尺寸） | 盖上半 | 盖下半 | 盖左半 | 盖中央 25% | 盖右下角 |
|---|---|---|---|---|---|
| char 角色（162×208） | 不认 | ✓ 0.56 遮挡 | ✓ 0.67 遮挡 | ✓ 0.89 | ✓ 0.89 |
| heart_1 红心（68×62） | 不认 | ✓ 0.33 遮挡 | ✓ 0.33 遮挡 | ✓ 0.67 | ✓ 0.56 遮挡 |
| coin 金币（40×54） | ✓ 0.44 遮挡 | ✓ 0.56 遮挡 | ✓ 0.44 遮挡 | ✓ 0.78 | ✓ 0.89 |
| minimap 小地图（315×275） | ✓ 0.33 遮挡 | ✓ 0.33 遮挡 | ✓ 0.33 遮挡 | 不认 | ✓ 0.67 遮挡 |

20 种遮挡认出 17 个，其中 16 个**框位置与真值完全一致**（另 1 个是金币被盖中央时在旁边的亮字形处
误定位，冷启动单帧才会遇到，连续调用有上一帧位置当提示就不会）。干净帧 `occluded` 名单为空
（不许把"完好无损"报成"被遮挡"）。

**分寸**：约四成以内认得稳；盖掉一半还常常能认出但会标 `occluded` 并压低置信度；盖到七成以上
就不猜了 —— 宁可说"不在"，也不给一个自信的错位置。

## 出现没编过的新东西呢？—— 会告诉你"哪儿多了块东西"

`cv_recall{novel:true}` 会把当前帧和**这个场景的参考帧**（`add_scene` 时顺手存的 320px 缩略图）
做差分，扣掉已知实体的框，剩下的连通块就是要报的东西：

```text
cv_recall{novel:true}
→   · 新东西：1 处 —— 黄色 80x72 @ 13%,77%
```

每项给 `{box, frac, color, at}`（全分辨率框、占屏比例、颜色、位置百分比）。**只发现不命名**：
它不知道那是个宝箱还是新怪，只知道"这儿比编译时多了块黄东西，约 80×72"。

实测（在真实截图上贴 70×70 / 120×120 / 90×90 三处亮块，分别贴空地、房间中央、角落）：
三处**全部命中**，颜色与位置百分比正确（框比贴的略大 8~10px，因为差分把边缘也算进去了）。
干净参考帧上 `novel` 为空（零误报）。整屏差异 >25% 时它会改成一句话
「整屏和参考帧差别很大（xx%）：多半换了房间/界面，不像只是多了个东西」—— 换房间本来就该
走场景切换，不该逐块乱报。

## 画面上的字呢？—— 用系统 OCR，中文也读；读不准就留空

数值走的是自己训的字形模型（见文末「内置字形识别器」），**普通文字**——对话框正文、
菜单项、按钮、提示——走 Windows 自带的 `Windows.Media.Ocr`：零第三方库、纯本地离线、
带每行的框、装了中文语言包就能认中文。两个通道分工明确：**系统 OCR 认"正常的字"，
字形模型认"系统 OCR 认不出的字"**（像素字、花体、超大描边），后者正是我们自己训模型
擅长的。

```text
cv_recall{text:true}            # 读下半屏（对话框/选项都在下面），默认这条带
cv_recall{text:"top"}           # 也可以 top / mid / full
cv_recall{text:[[120,460,1080,200]]}   # 或自己给框
```

```text
→   · 文字（bottom）：
      「巨响从走廊深处传来，你握紧了武器。」  text [123,467,455,28]
      「生命：82/100」 = 82/100  stat [120,517,191,27]
      「继续」  button [121,580,79,39]
      「离开」  button [421,578,79,40]
```

每块给 `{text, box, kind, value?, id}`：`kind` 是 `button`/`stat`/`number`/`title`/`text`
这类粗分类（关键词表 + 几何位置），`value` 只有在"这一块里就一个数"时才给，`id` 用
「类型 + 文本 + 48px 位置桶」算，所以**同一个人连续帧里 id 不变**，可以直接拿来记住
"上次点的那个按钮"。

### 怎么保证它不瞎编

系统 OCR 遇到像素字、花体、发光描边**不会报错，而是吐一堆"看着像字"的胡话**，而且换个
缩放就换一套胡话。所以这里做了三道闸：

1. **单行过滤**：行太矮/太高、一个字母数字都没有、一行里字高忽大忽小（`hs` = 字高标准差
   ÷ 平均值）的都丢掉。实测真文字 `hs` 在 0.02~0.16，把 HUD 图标当字读出来的垃圾行在
   0.42~0.67，门限 0.30 干净分开。
2. **整片否决**：一片区域里大多数行都"字高乱跳"，就判定这整片不是文字，**一行都不采信**
   —— 宁可不读，也不把胡话拼成一句话交出去。
3. **换缩放三局两胜**：同一区域在 3 个缩放下各读一遍，同一位置至少两遍读到同样的东西
   才算数；三遍读到的最优文本按票数选，平票取更短的（OCR 更容易多吐字，而不是少吐）。
   这一条顺带修掉"某个缩放下某个字被读坏"的偶发错误（实测 2.0 倍把 `取消` 读成 `取氵肖`，
   2.25/2.5/3.0 都对，投票后就选对了）。

代价是 OCR 跑 3 遍，所以**读文字要显式要**，别每帧都开。

实测（本机，2559×1599 真实截图）：合成中文对话框下半屏 **冷 0.70s / 热 0.21s** 读出 4 段
全对、分类全对；《以撒》的像素字 HUD（下半屏 89ms、整屏 188ms）**输出空**并附一句
「这一片看不出像文字（系统 OCR 只读出零散噪点，已丢弃）」——这是正确的行为，
不是失败。金币计数指定 `alphabet:"digits"` 时 50ms 读出 `00`，走的是字形模型。

**限制**：只读横排文字（竖排不支持）；半透明叠字等动画停了再读；字体是像素/花体/发光
描边时系统 OCR 基本认不出（此时给数字字段指定 `alphabet`，或把这块字当图标去编实体）；
字母会互相认错（`World` → `WorId`）；要文字之间有间隙、高度一致，一行里混排大小字体会碎。

## 它凭什么认得准

每个实体编译时都会测两类证据，权重由**可分离度**决定（正样本 vs 负样本分得开才给权重）：

1. **两路归一化互相关**：灰度路（看整体明暗）与边缘路（看边框/刻度线）。
   血条掉血会毁掉灰度路，但边缘路只掉 0.10；面板换内容则相反 —— 所以两路分开投票，
   不搞"平均一下"。
2. **分块多数票**（`ncc_t`）：把模板切 3×3，只看最好的 1/3 块。
   整块 NCC 是平均分（面板换掉一半内容就掉到 0.38），分块投票是多数票（同帧 0.85）。
3. **场景 = 实体存在向量 + 全局直方图**，离得太远直接报 `unknown` 而不是硬猜。

负样本是**免费**的：同一帧里其它位置、其它实体的位置天然是负样本；`add_scene` 时
「这一帧里该在的」提供了正样本的真实下限，「肯定不在的」提供了必须压住的上限 —— 阈值因此
落在真实分布上，而不是「校准帧 = 1.0」这种假前提上。

## 诚实的限制

- **只做判别 + 读字形，不做理解**：它知道血条在哪、数字是几，不知道"这一下打掉多少血"意味着什么。
- **字形图集本身只认编译时给它看过的字**（参考图里只有 0/1）。但图集认不出时会自动问内置的
  小分类器，所以换个数字通常还能读出来；两个都拿不准才输出 `?`。想更稳就再 `build` 一次，
  同一格 `digits` 给新 value，图集会合并。
- **内置识别器只读"亮字、高度一致、字之间有间隙"的字**：深色描边字、混大小写、被标点分隔的
  串（`00:01:00`）它会切错段。游戏里最常见的大写 HUD 数字/词条是它的目标场景。
- **字体不能混**：HUD 的粗体字与世界坐标的细体数字是两套字形，混进同一图集会互相误判
  （实测细体 `2` 只有 0.52 分，还会把粗体 `0` 判成 `2`）。同一包请只收同一套字体。
- **容器类控件**（对话框/背包面板）内部内容整块替换时会漏。`build` 会主动打 `⚠` 提示，
  正确做法是标它内部稳定的子部件（标题栏/按钮/边框），或在内容不同的第二张画面上 `add_scene`。
- **遮挡有上限**：约四成以内认得稳，过半常能认出但会标 `occluded` 并压低置信度，七成以上不猜。
- **"新东西"只在同一场景里管用**：它靠"与这个场景参考帧的差分"，所以换房间/换界面会先说
  "整屏差别很大"，而不是逐块乱报；没 `add_scene` 过的场景不做这件事。
- **换主题 / 改分辨率 / 改 UI 缩放** ≈ 资产报废。工具会自己报 `stale`，不会静默错答 ——
  这时 `add_scene` 补一帧就好。
- **独占全屏 / 反作弊顾问可能报错**：拓展超出了 PrintWindow 能拿到的东西，这类窗口的帧会是黑的（工具会报“空帧”，不会自己发明一张图）。
- **提权窗口点不了**：UIPI 会把 SendInput 拦在低权限进程下，这时会报 `UIPI`，而不是假装点成了。
- 延迟是**纯 numpy** 的量级：11 个实体 1280x720 约 50~85ms（本机 4 线程实体级并行）。
  没到设计时想要的 20ms，原因是 NCC 的 FFT 与缩放占了八成时间；要更快只能靠原生扩展。

## 真实截图验证（《以撒的结合》，2559x1599）

只用**多模态看一张参考图**给出 6 个框，编译成包，然后盲测另外 4 张（这 4 张编译期从未被
读取）。结果按实体统计：

| 实体 | 命中 | 说明 |
|---|---|---|
| hearts / coin / bomb / key | 4/4 | HUD 图标，真位置全对 |
| char（角色以撒） | 4/4 | 其中一张角色贴在画面左缘、被切掉一半，仍然认出来了 |
| map_tl（小地图左上角框） | 4/4 | 静态子部件，内图整块重画也不受影响 |
| minimap（小地图整块） | 2/4 | 未中：内部从 3 格暗块换成彩色展开图，整块 NCC 掉到 0.05 |

**7 个实体 × 4 张 = 28 次判定，命中 26 次（92.9%）**；去掉容器类的 `minimap` 是 **24/24**。
场景判定 4/4 全对（同一房间的不同时刻，`scene_dist` 0.023~0.151），无误报的 `stale`。
每帧 150~194ms（7 个实体 / 2.5K 分辨率，纯 numpy）。

这张表就是「容器类要标静态子部件」这条建议的实验证明：同一块小地图，标整块 2/4，
标左上角那段 L 形黑框 4/4 —— 像素级对比显示角框在两张图之间完全一致，只有内部不同。

### 内置字形识别器：图集缺字不再输出 `?`

只学一帧的图集有个硬伤：参考图里只有 `0` 和 `1`，画面冒出 `2` 就只能给 `0?`。为此插件里带了
一个**自己的小型字形分类器**（`sidecar/pcv/ocrlib.py` + `ocr_digits.npz`，380KB）：

- 训练素材全在本地：`C:\Windows\Fonts` 里 84 种字体渲染 0-9A-Z，加程序生成的七段/LED 块字
  （《以撒》这种粗描边像素字属于这一族），再做加粗/变细/平移/拉伸/像素翻转的增强。
- 纯 numpy 前向（768-128-36 小 MLP），**不联网、不调用任何模型**，单字 <1ms。
- 实测（**留出 30 种训练时没见过的字体**）：只允许数字 **86.5%**、七段块字 **99.3%**、
  全 36 类 **76.1%**。数字稳、字母一般 —— 所以它只在**明显有把握**时采信（top1 概率与
  top2 间隔双门限），否则仍然输出 `?`，绝不猜。

它和图集是**主副关系**：图集（编译时人给的那次 value）永远优先，1.0 分就是 1.0；图集没有这个
字形时才问小模型。所以「同一个字体换个数字」这种最常见的漂移能直接读出来，而不会悄悄读错。

顺带做了两件事：

- `pick["text"] = {box:[x,y,w,h], value:"BOMB"}` —— 和 `digits` 同一套机制，但输出留字符串
  （店价签、道具名、提示语）。要求这块字高度一致、字之间有间隙；混大小写和冒号这类符号不行。
- `cv_recall{text:[[x,y,w,h]]}` —— 不用编译、不用学，直接读任意一块区域上的文字（最多 6 块）。
  实测对 Arial Bold 这类系统字体基本一次读对（`BOMB` / `KEY12` / `TRUE`）。

**Windows 自带 OCR 为什么不用**：它不是坏，是压根不认这类字体 —— 在以撒的像素字上试了 20 种
预处理（4 种缩放 × 2 种重采样 × 2 种极性 × 2 种细化）全部返回空串，而同一套桥读 Arial 一读就中。
Tesseract 要另装几十 MB 二进制与训练数据，对同一种字体也未必比这个 380KB 的小模型强。
